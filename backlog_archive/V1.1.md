# Plan V1.1 — US3D plugin project

## Status and scope

The high-level workflow below was agreed during task-by-task review and reconciled with the backlog at the user's request. Equation-specific details and the later sensitivity/release breakdowns remain open. This document governs the revised workflow; `planV1.0.md` remains unchanged as a historical reference.

- Backlog task scopes and dependencies now reflect this plan. Existing IDs and prior progress were preserved where applicable; superseded candidate-specific tasks were archived, not marked complete.
- Numbers below identify plan sections, not existing Backlog task IDs. The final numbering/organization remains undecided.
- Keep assignments bounded enough for agents such as Terra or Sonnet: one objective, explicit inputs, a concrete deliverable, checkable completion criteria, and clear stop conditions.
- Separate knowledge-base preparation from choosing equations, deciding the solver architecture, writing the project plugin, and executing simulations.

## Environment and evidence boundaries

- US3D is not installed on this computer and will not be installed here.
- This computer supports reference analysis, development, and checks that do not require US3D.
- The user has example plugins and prepared simulation cases that can be added as reference materials. Inventory their availability rather than assuming they are already present.
- Build/load checks, baseline execution, and numerical verification require a separate target environment. Instructions can be prepared here, but local static inspection cannot satisfy those runtime checks.
- Distinguish evidence explicitly: **documented in a manual**, **shown in example source/input files**, and **verified by execution**. Record unknowns and version conflicts rather than inferring support.
- Manual summaries are navigation aids. Exact interface and configuration claims should trace back to original manual pages or supplied files.

## Initial setup tasks

### 1. Take inventory of what is necessary

**Purpose:** Establish what reference materials are needed, what is available, and what is missing.

**Inputs:** Existing reference library and any example plugins or prepared cases supplied by the user.

**Deliverable:** An inventory listing manuals, example plugins, prepared cases, known versions, paths, provenance where available, and missing materials or information. Explicitly record the no-local-US3D constraint.

**Completion checks:**
- Each required material is identified as available, missing, or not yet confirmed.
- Available items have locations and known versions; unknown versions are labeled as such.
- Prepared cases and source examples are not represented as runtime-verified merely because their files are present.

**Boundary:** Inventory identifies what we have; tasks 4 and 5 explain how to use it. Missing materials are reported, not fabricated.

### 2. Create a searchable reference from the manuals — completed

**Purpose:** Make future manual lookup easier without repeatedly reading the full PDFs.

**Existing deliverables:** Chapter/appendix summaries, a chapter index, a cross-manual topic guide, and provenance/validation notes with links back to source pages.

**Entry points:**
- `.pi/ref-library/README.md`
- `.pi/ref-library/summaries/README.md`

**Existing tracking:** TASK-3, completed. Reuse this work; do not repeat the manual summarization effort.

**Boundary:** These references describe documentation, not a tested installation. Preserve recorded extraction, review, and version limitations.

### 3. Prepare a specialist workflow for matching equations to US3D hooks

**Purpose:** Once equations are established, identify candidate places where a plugin can connect to US3D, the information it needs, and unresolved capability questions.

**Form:** A specialized research agent using skills and shared references.

**Existing work:** Four supporting skills already exist: `equation-to-requirements`, `manual-evidence-search`, `hook-capability-mapping`, and `hook-report-review`. Existing TASK-2 records this partial progress. The complete agent workflow and fixture evaluation remain unfinished.

**Inputs for future use:** User-supplied equations and assumptions, required quantities, and target US3D version or an explicit unknown.

**Deliverables:** A usable specialist workflow and small fixture-based checks demonstrating evidence-backed recommendations, bounded searches, and honest handling of missing or conflicting evidence.

**Completion checks:**
- Recommendations explain the required data and candidate integration points, with source citations.
- Missing support and version conflicts are labeled unknown or blocked, not invented.
- Small checks cover supported, missing, and conflicting candidates without requiring full-manual searches for every routine test.
- Outputs distinguish documentation evidence from capabilities verified on a target installation.

**Boundary:** The workflow can be prepared now. Project-specific recommendations wait for established equations. It does not choose the project's physics or prove an installed solver supports the proposed integration. Its completion is not required to perform an equivalent manual, evidence-backed audit.

**Assignment sizing:** Review remaining agent integration, bounded evidence retrieval, and evaluation as separate execution slices before implementation; do not hand the entire unfinished feature to an agent as one open-ended assignment.

### 4. Create a reference guide and skill for writing plugins

**Purpose:** Explain how to write a US3D plugin using documented interfaces and supplied examples.

**Form:** A durable reference guide paired with a plugin-writing skill. A dedicated plugin-writing agent is not required for this setup stage.

**Inputs:** Manuals, existing searchable summaries, and user-supplied example plugins.

**Reference content:**
- How plugins are organized and where US3D calls them.
- How demonstrated examples read information and supply changes.
- Relevant example files and code locations for each pattern.
- Known version constraints, missing information, and checks requiring the target installation.

**Skill behavior:** Direct an agent to the relevant reference sections, use supported patterns, identify missing requirements, and stop rather than invent an interface.

**Completion checks:**
- Guidance traces to manual pages or supplied example source.
- Documented capabilities and example behavior are distinguished from runtime evidence.
- A small worked-example check exercises the guidance without claiming compilation or execution.

**Assignment sizing:** Inspect one example plugin per bounded assignment, then consolidate reusable findings into the guide and skill. The knowledge-base task does not write the actual project plugin.

### 5. Create a reference guide and skill for writing input files

**Purpose:** Explain how to prepare US3D case inputs using documented settings and supplied cases.

**Form:** A durable reference guide paired with an input-file-writing skill. A dedicated input-writing agent is not required for this setup stage.

**Inputs:** Manuals, existing searchable summaries, and user-supplied prepared cases.

**Reference content:**
- Files and settings needed for a case.
- Required versus optional settings and how they relate to the selected physical models.
- Relevant example files and settings.
- Common omissions, documented incompatible combinations, missing dependencies, and known version constraints.

**Skill behavior:** Ask for necessary case details, select an appropriate example, and perform checks that are possible without running US3D. Report missing information rather than silently choosing consequential physical settings.

**Completion checks:**
- Guidance traces to manual pages or supplied case files.
- Each reviewed case has an explanation of its purpose, relevant inputs, and missing pieces.
- A small worked-example check exercises the guidance without claiming that US3D accepts or runs the resulting inputs.

**Assignment sizing:** Inspect one prepared case per bounded assignment, then consolidate findings into the guide and skill. The knowledge-base task does not produce the project's production input file.

## Post-setup workflow decisions

- Remove the proposed agent task **“Check the proposed model’s assumptions.”** The user will perform the physical-model assessment offline; this does not remove setup task 2 (the completed manual reference).
- Treat the user's selected equations, assumptions, applicability limits, and model decisions as inputs to the agent workflow. Do not require an agent-generated model-assessment report.
- The agreed handoff is: **describe the target problem → document the user-selected equation set for approval → assess candidate US3D hooks**.
- Agents may flag missing definitions or inconsistent supplied information and request clarification; they must not silently select or change the physical model. Recording the equations does not constitute independent validation of their physical suitability.

## Problem definition and equation-specific hook assessment

### Describe the target problem

**Inputs:** User-supplied geometry or representative case, flow and gas conditions, magnetic-field conditions, relevant physical boundaries, research questions, and existing modeling constraints. Inputs may initially be incomplete.

**Outputs:** A target-problem specification identifying the intended conditions, quantities to compare, known inputs with units and sources, uncertainties, and questions for the user. Proposed representative values are distinguished from approved values.

**Completion:** The user confirms that the specification describes the intended problem. Missing information that prevents downstream work is explicitly identified; documenting a blocker does not resolve it.

**Boundary:** Do not select the physical model or investigate plugin hooks in this task.

### Document the user-selected equation set

**Inputs:** The target-problem specification; the ordered list of equations supplied by the user, including the intended calculation/update order; assumptions, applicability limits, and modeling decisions supplied by the user following their offline assessment; and primary references defining the equations. No agent-generated physical-model assessment is required.

**Outputs:** An equation specification containing governing equations, solved and prescribed quantities, variable definitions and units, sign conventions, required properties, applicable initial/boundary conditions, force and energy terms, energy accounting, exclusions, and unresolved questions.

**Completion:** The user approves the specification. Unresolved physical choices that prevent hook assessment keep it in draft status.

**Boundary:** Clarify missing definitions without silently selecting or changing the physics. This task does not choose numerical methods, implement code, or independently validate the model's physical suitability.

### Identify candidate US3D hooks for the approved equations

**Inputs:** The approved equation specification, target US3D version or explicit unknown, manual references, and relevant example-plugin evidence.

**Outputs:** An equation-to-hook mapping showing required inputs/outputs, candidate interfaces, lifecycle timing, units and data locations where documented, parallel/boundary considerations, source citations, version conflicts, and unresolved support questions.

**Completion:** Every equation requirement has an evidence-backed candidate connection or an explicit unknown/blocker. The mapping distinguishes documented/example support from target-system verification.

**Boundary:** This task uses the specialist prepared in setup task 3, or an equivalent bounded manual audit; it does not rebuild the specialist. A completed report with blockers is not approval to implement unsupported connections. Resolve those blockers or obtain approval for an alternative before affected implementation begins.

## Agreed initial plugin implementation and regression tasks

### Initialize supported hooks and plugin variables without physics operators

**Purpose:** Turn the equation-specific data-connection design into a minimal plugin that initializes the required supported hooks and variables without changing the flow calculation.

**Inputs:**
- User-approved equation specification.
- Equation-specific hook assessment.
- Relevant manuals and example-plugin references.
- Target US3D version, or an explicit unknown that must be resolved wherever interface compatibility depends on it.

**Outputs:**
- A data-connection table documenting each required quantity, meaning, units, cell/face/global location, intended read/write behavior, supported interface, and unresolved verification needs.
- Minimal plugin source that registers/initializes the supported hooks and required variables using documented patterns.
- Documented initialization values and build/load instructions for the target environment.
- Available static checks and a list of checks that require US3D.

**Completion checks and boundaries:**
- Each implemented connection is traceable to documentation or supplied example source; unresolved interfaces are blockers, not invented implementations.
- Initialize plugin-owned quantities without overwriting the baseline flow state.
- No new physics operators, potential solve, forces, heating, or other physical coupling are applied. Hook callbacks remain inactive with respect to the simulation equations.
- Record local static-check evidence separately from target-environment build/load evidence. Do not claim the plugin compiles, loads, or preserves results based only on source review.

**Assignment sizing:** Keep the data table and minimal initialization scaffold bounded; if the number of interfaces is large, divide implementation by coherent groups of variables/hooks rather than adding physics to this task.

### Verify that the initialized, operator-free plugin does not change the simulation

**Purpose:** Establish a no-op regression before introducing physics operators.

**Inputs:**
- The initialized, operator-free plugin from the preceding task.
- A selected prepared case and all required run inputs.
- Access to a separate target US3D environment through the user or another explicitly arranged execution route; no local US3D installation is expected.
- Target version/build information and a documented comparison procedure with justified numerical tolerances.

**Outputs:**
- Reproducible target-environment instructions for building/loading the plugin and running the same case without the plugin and with its hooks/variables initialized.
- External execution evidence: commands, configuration, logs, relevant outputs, and version/build details.
- A comparison report covering agreed flow quantities and convergence behavior, with an explicit pass/fail result or unresolved blocker.

**Completion checks and boundaries:**
- The plugin builds and loads on the target installation.
- Baseline and plugin-enabled runs use equivalent case inputs and execution settings apart from the plugin activation.
- Flow results and convergence behavior agree within documented, justified numerical variation; differences are investigated rather than hidden by loosening tolerances.
- The report confirms that no new physics operators were active.
- Preparing instructions locally is not completion of this verification task. It remains unverified until target-system execution evidence is available.
- A failed no-op regression blocks adding physics operators until the cause is resolved.

## Equation-by-equation implementation

After the initialized-plugin no-op regression passes, create one task for each equation in the user-approved specification. Each equation task has two separately checkable parts that can be assigned individually to an agent. Actual equation names and task counts will be determined from that specification, not assumed from the candidate model.

### Part 1 — Calculate and test the quantities

**Inputs:** The approved equation, variable definitions and units, required properties and boundary conditions, agreed numerical method where needed, and prescribed test inputs with independently justified expected results.

**Outputs:** Calculation code, documented inputs/outputs, and reproducible tests comparing calculated quantities against analytic values, manufactured solutions, or other appropriate independent references.

**Completion checks:**
- The calculation has explicit units, sign conventions, and behavior for relevant limiting or invalid inputs.
- Tests exercise the equation's relevant behavior without feeding its new effects into the US3D flow calculation.
- Tests run independently of US3D where feasible. Mesh-dependent or solver-dependent checks that cannot run locally are identified explicitly and require target-environment evidence.
- An undecided numerical method, unavailable input, or unresolved interface is a blocker to clarify, not a choice an implementation agent silently makes.

### Part 2 — Integrate the equation into US3D

**Inputs:** The tested calculation from part 1, approved data connections and update sequence, the no-op-verified plugin, and outputs from any prerequisite equations.

**Outputs:** Plugin integration that reads the required US3D state, performs the calculation at the approved point in the update sequence, and stores or applies its results as specified; target-environment test instructions and execution/comparison evidence.

**Completion checks:**
- Verify units, data locations, update timing, and intended outputs or source terms.
- Compare integrated results with the part-1 reference cases where applicable, and rerun relevant earlier regressions.
- Confirm disabled behavior preserves the established baseline; use equation-appropriate conservation and consistency checks when enabled.
- Actual US3D integration verification requires evidence from the external target installation. Local preparation or static review alone is not a passing integration test.

### Dependencies and assignment boundaries

- Follow the user's supplied equation order and record it in the shared equation specification. Track dependencies explicitly; an equation that needs another equation's output cannot be treated as independently integration-ready. If the supplied order conflicts with a required dependency or supported US3D lifecycle, ask the user rather than silently reordering equations.
- Part 1 may use prescribed inputs to isolate a calculation. Part 2 must check its real data connections.
- Not every equation adds a force or heating term: some supply properties, fields, or intermediate quantities. Integrate only the behavior specified for that equation.
- Separate equation tasks do not eliminate the need for later coupled-system verification, including charge and energy accounting where applicable.
- Keep each agent assignment limited to one equation and one part. Decompose further if an individual spatial solve is still too large.

## Canonical-case verification

After the required equations have been individually tested and integrated, verify that they work correctly together using canonical cases with known reference solutions. Create one bounded task per canonical case. Select cases whose assumptions match the user-approved equation set; Hartmann channel flow is a candidate, not an automatic requirement.

### Verify the coupled plugin using a canonical case

**Inputs:**
- The integrated plugin and evidence from prerequisite equation tests.
- A canonical-case definition, including geometry, physical assumptions, initial/boundary conditions, and required properties.
- A sourced reference solution and agreed comparison measures and tolerances.

**Work:** Prepare the case and comparison procedure, execute it on the external target US3D installation, and analyze the returned results against the reference solution. Perform relevant conservation checks and refinement comparisons appropriate to the selected case.

**Outputs:**
- Reproducible case files and target-system run instructions.
- Execution evidence, including version/build details, settings, logs, and results.
- Comparison plots and error measures, relevant conservation checks, and a pass/fail report with unresolved discrepancies explicitly identified.

**Completion checks and boundaries:**
- The simulated problem matches the assumptions and boundary conditions of the reference solution.
- Results satisfy the agreed comparison criteria; failures are investigated rather than silently changing the reference or tolerances.
- Preparation and result analysis can occur locally, but US3D execution and runtime evidence must come from the external target installation.
- A canonical case verifies the selected coupled equations; it does not by itself validate hypersonic chemistry or RF/blackout predictions.
- Canonical verification precedes the hypersonic application demonstration.

## Hypersonic application demonstration

After canonical-case verification passes, perform a first bounded comparison of a selected hypersonic case without and with an applied magnetic field. Keep this initial demonstration separate from any later sensitivity campaign.

### Compare no-field and applied-field hypersonic cases

**Inputs:**
- The verified plugin and canonical-case verification evidence.
- The user-selected hypersonic case, including required files, physical conditions, and boundary conditions.
- Agreed magnetic-field conditions and quantities to compare.
- The approved model's applicability limits and relevant conservation diagnostics.

**Work:** Prepare equivalent no-field and applied-field configurations, execute them on the external US3D installation, and analyze the returned results. Keep other settings equivalent so differences can be attributed to the applied field.

**Outputs:**
- Reproducible case files and target-system run instructions.
- External execution evidence with version/build details, configurations, logs, and results.
- Comparisons of the agreed quantities, such as electron density, flow changes, forces, and heating where supported by the approved model.
- Relevant conservation and model-applicability checks, with limitations and unresolved issues explicitly reported.

**Completion checks and boundaries:**
- Both configurations run successfully on the target system and produce the agreed comparison evidence.
- Report the observed response without requiring a favorable magnetic-window effect as a condition of completion.
- Do not equate changes in plasma or flow quantities with verified RF attenuation or blackout mitigation.
- This task covers one initial comparison, not a mesh/timestep/field-strength/conductivity sensitivity campaign or a claim of numerical independence.
- Case preparation and result analysis can occur locally; runtime verification requires external execution evidence.
